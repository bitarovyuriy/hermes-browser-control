# Hermes browser extension — merged MVP

One loadable MV3 extension that combines three parts:

| part | what it is |
| --- | --- |
| CDP browser control (carrier) | the whole `extension/` tree: `chrome.debugger` + CDP forwarding, the banner-free content-script path, access modes, session control, artifacts, on-page HUD, control page |
| Loopback relay transport | `extension/vendor/transport/*` (pairing, WS session, backoff, heartbeat, command queue, redacting logger) wired into a single `src/relay-host.js` |
| Operation guard | `security/operation-guard.mjs` + `lib/sensitive-domains.mjs`, wired onto the live command path by `src/admission.js` |

    relay/                         loopback relay (vendored: pairs the extension with the
                                   runtime, mints tickets, forwards commands)
    extension/                     loadable unpacked MV3 extension
      manifest.json                permissions: debugger, tabs, tabGroups, storage,
                                   alarms, nativeMessaging; host perms are a
                                   loopback allowlist (no <all_urls>, no activeTab,
                                   no scripting, no contextMenus)
      background.js                service worker: controller + admission guard + relay host
      src/
        controller.js              chrome-shaped glue (patched: consults `admission`)
        admission.js               *** new *** the guard on the command path
        relay-host.js              *** new *** the transport grafted into this worker
        access-policy.js           which tabs the agent may touch (pure)
        session-state.js           armed / paused / killed, grant, revocation (pure)
        cdp-methods.js             CDP allowlist + param validation (fail-closed)
        command-router.js          agent verb -> {content path | CDP path} (pure)
        artifacts.js               artifact store (pure)
        fallback.js                content-script bridge (chrome.tabs.sendMessage)
      content/content-script.js    DOM verbs + HUD / element badges / agent pointer
      icons/                       icon-16/32/48/128.png — the black-on-white artwork as
                                   drawn, generated by tools/make-icons.py from the source
      control/                     the control page — `popup.html` (the toolbar popup)
                                   and `control.html` (the same page as the options
                                   page): live state, the relay phase, Pause / Resume /
                                   Reconnect, Kill switch
      security/operation-guard.mjs deny-list + profile/port freshness lease (pure)
      lib/sensitive-domains.mjs    the single sensitive-domain rule list
      vendor/transport/*.js        the transport workstream, verbatim (compiled ESM)
    tools/
      install-native-host.mjs      per-user native-messaging install (HKCU + %LOCALAPPDATA%)
      native-host/relay-host.mjs   the installed, dependency-free host (parity-tested)
    test/unit/                     60 unit tests + 11 security tests (node --test)
    test/e2e/e2e.mjs               42 checks: real Chrome, driven over the worker's own
                                   message surface (the relay's entry point); the only page
                                   it drives is the control page — state read + kill click
    test/e2e/relay.mjs             41 checks: real Chrome + the real loopback relay,
                                   including a live internet page (https://example.com)
                                   navigated, read and screenshotted through the relay,
                                   and the session established over `hermes/relay`
                                   (+22 more with `--native-host`: the real native-messaging
                                   install, paired with no manual string at all)

## Why this base and not the TypeScript scaffold

An earlier TypeScript scaffold is a parallel product shell whose CDP handler and
transport were stubs. This tree is the artifact that already performed the MVP
behaviour end to end in real Chrome, and both other workstreams were built to drop
into it (the CDP worker already advertises the `hermes-relay` port and the
`globalThis.hermesRelay` artifact sink; the transport is plain ESM with an
`onCommand` hook; the guard is a pure module). Merging here means the MVP rests on
code that is verified, not on a rewrite. `test/e2e/`, the release packaging and the
scaffold remain valid in their own trees.

## Load it

    chrome://extensions -> Developer mode -> Load unpacked -> pick `extension/`

Click the toolbar action to open the **control popup** (`control/popup.html`); the same
page is available as the extension's options page (`control/control.html`) from its entry
in `chrome://extensions`, and from the popup's "Open as a full page" link. It is the human
stop, not a cockpit: the session state the worker reports,
the relay phase, and the switches — **Pause**, **Resume**, **Reconnect**,
**Kill switch**, **Clear kill**.

## Use it as a Hermes skills tap

This repository doubles as a [skills tap](https://hermes-agent.nousresearch.com/docs):
`skills/hermes-browser-control/SKILL.md` teaches a Hermes agent how to install the
extension, pair it and drive it safely.

    hermes skills tap add <owner>/<repo>
    hermes skills install <owner>/<repo>/hermes-browser-control

## How the agent is driven (and why the page is this small)

The Hermes runtime drives this browser **over the loopback relay**: the runtime
issues the commands, the worker executes them, and the extension never needs a
human in the loop. That is why the page carries no command box, no pairing form
and no tab grant list — those were the old side panel, and none of them were ever
on the agent's path.

* **Pairing** is the native host's job (`local` mode, nothing to paste). A manual
  `hbr1:<base64url>` string still exists as a message-surface action
  (`hermes/relay` → `pairingString`) for tooling that has to pair by hand: held in
  memory only, never written to storage, never rendered on the page, never logged.
* **Arming** is automatic: `agent-all` when the relay reports `connected`,
  `tab-group` when the agent opens its own tab. Nothing to click.
* **Artifacts** flow to the runtime sink over the relay; the worker also keeps a
  bounded ring buffer, reachable as `{type: 'hermes/artifacts'}`.
* **The page talks to the worker only over the message surface**
  (`{type: 'hermes/state'}` and `{type: 'hermes/relay', payload: {action: …}}`),
  and polls it every 2 s so an idle-worker restart cannot leave a stale `armed` on
  screen.
* **Pause / Resume / Kill** on the page drive both halves at once: pause closes
  the relay socket (`phase: paused`; the relay drops the extension session),
  resume re-arms it, and the kill switch tears the transport down (`phase: fatal`,
  terminal). A session ticket is single-use, so resume alone re-pairs with a spent
  string and cannot reach `connected` again — that is what **Reconnect** (native
  host) is for.
* **The agent's commands never come from a page.** They arrive as
  `{type: 'hermes/command', command, opts}` on the worker's message surface —
  exactly what the relay and the E2E harness send.

## Native messaging (what makes `local` mode work without a pairing string)

`local` mode pairs through the native host `com.hermes.browser_relay`. Nothing
registers that host by itself — until you install it, `local` mode only works
from a pairing string handed to the worker over `hermes/relay`, and the extension
says so instead of quietly sitting in `reconnecting`.

    npm run native-host:install     # per-user: HKCU + %LOCALAPPDATA%, no admin
    npm run native-host:check       # verify the install; exits 1 on drift
    npm run native-host:uninstall   # remove the manifest, launcher and HKCU values

What the installer writes (every path derived at install time, nothing
user-specific is committed):

* `%LOCALAPPDATA%\hermes\native-messaging\com.hermes.browser_relay.json` — the
  host manifest, `type: stdio`, `allowed_origins` limited to
  `chrome-extension://<id>/` for the id Chrome assigns this `extension/` tree,
* `…\com.hermes.browser_relay.bat` — the launcher Chrome execs: absolute paths
  for `node.exe` and the host script, no `PATH` lookup, no shell expansion, and
  every failure appended to a log (Chrome throws a native host's stderr away),
* `HKCU\Software\Google\Chrome\NativeMessagingHosts\com.hermes.browser_relay`
  and the `Chromium` equivalent — **per-user, no elevation, nothing in HKLM**.

The unpacked-extension id is not hardcoded and not guessed: it is Chrome's own
derivation (SHA-256 of the absolute extension path, UTF-16LE, first 16 bytes in
the `a–p` alphabet), and `npm run test:relay:native` asserts the number it
derives equals the one `chrome.runtime.id` reports.

Chrome for Testing 154 was measured to read the `Google\Chrome` and `Chromium`
keys and to ignore its own product key (`Software\Google\Chrome for Testing\…`),
which is why `--browsers` offers exactly those two families.

## Run the verification

    npm test           # 60 unit tests (54 CDP + 6 native-messaging) + 11 security tests
    npm run scan:secrets  # required CI gate: no secret-shaped literals in the tree
    npm run test:e2e   # 42 checks in real Chrome, driven over the worker's own surface
    npm run test:relay # 41 checks in real Chrome through the real relay
    npm run test:relay:native  # the same, plus the real HKCU native-messaging install
                               # install — the host is registered, Chrome is launched, and
                               # the extension must reach `connected` from the native host
                               # alone. Writes HKCU + %LOCALAPPDATA% and uninstalls after.
    npm run test:all   # test + scan:secrets + e2e + relay

Chrome is discovered from `CHROME_PATH`, then the local puppeteer cache, then the
usual install locations — nothing is downloaded. `HEADED=1` runs windowed.
`npm run test:relay` uses the relay that ships in this repository (`relay/relay-cli.ts`;
point `HERMES_TRANSPORT_DIR` at the upstream transport checkout to test against that
instead). It starts the real relay on a free port
and gives it a private `%LOCALAPPDATA%`, so concurrent runs never fight over the
rendezvous file. The native suite needs the same checkout for the host-parity
check in `npm test`.

CI (`.github/workflows/ci.yml`) makes `npm test` and `npm run scan:secrets` required;
the browser suites are best-effort on the runner.

## Package and ship it

This tree is the release source of truth. The release toolkit lives in `release/` and
packages **only** `extension/`:

    bash release/scripts/build-release.sh --allow-dirty   # -> release/dist/*.zip + unpacked/
    bash release/scripts/verify-package.sh                # static gate on the artifact
    bash release/scripts/smoke-load.sh                    # loads it in real Chrome (CDP)
    python release/scripts/check_permissions.py           # manifest <-> justification drift
    bash release/scripts/hosts-inventory.sh               # outbound hosts (privacy honesty)
    bash release/scripts/pack-crx.sh                      # signed .crx (self-hosted channel)

Store copy, privacy policy, permission justifications, screenshot list and the release
checklist live under `release/`. See `release/README.md`.

An earlier reference fork and a TypeScript scaffold are kept as references only — they
are not packaged and are not part of the MVP.

## The relay path

    POST /browser/pair   -> one-time ticket (hbrt_, TTL 120 s, single use)
    POST /browser/echo   -> {method, params} injected into the extension, result returned
    GET  /browser/status -> live session snapshot
    WS   /browser/extension  <- the extension dials this
    WS   /browser/runtime    <- the Hermes runtime dials this

In the extension: mode `local` pairs through the native host
(`com.hermes.browser_relay`, registered per-user by `npm run native-host:install`),
any mode accepts a manual pairing string (`hbr1:<base64url>`), held in memory only. The message surface is the front end
for this: `hermes/relay` writes the settings, hands the pairing string over and
reads the phase back — `test/e2e/relay.mjs` establishes the whole session that
way, and the control page renders the phase it polls back. Every runtime
command is mapped onto the CDP command vocabulary: `{method, params:{tabId,
...args}}` -> `controller.execute({name: method, tabId, args})`.

## The guard

`src/admission.js` runs before `planCommand`, so a denied command never reaches
the CDP or content path:

* **Deny-list (both paths).** The target URL (the `navigate` target, otherwise the
  tab's current URL) is classified by `lib/sensitive-domains.mjs`: banking,
  crypto, password managers, email, government/tax, medical, credential surfaces
  and checkout are refused with `code: sensitive-domain`. An unparseable URL is
  refused too.
* **Freshness lease (relay path only).** `handleStatus` registers the live
  `{profileId, port}` binding; arming a session copies it into the lease. A relay
  command whose lease no longer matches the live binding is refused with
  `stale-port` / `stale-profile` instead of running against the wrong runtime.
  Without a binding the relay path fails closed (`no-lease`); the local page /
  harness path has no connection to be stale against, so only the deny-list
  applies there.
* `openTab` is gated too, and the kill switch tears the transport session down
  (`relayHost.kill()`), so a killed agent is unreachable from the runtime.

## Known limits

* Firefox has no `chrome.debugger` equivalent — chat only, no attach.
* The content-script (banner-free) path is declared for the loopback origins only;
  arbitrary user tabs go through the CDP path, which is why `debugger` is
  requested.
* `chrome.debugger.attach` fails with `debugger-busy` when DevTools is already
  attached to the same tab.
* The native-messaging host is only registered once you run
  `npm run native-host:install` — the installer lives in this tree
  (`tools/install-native-host.mjs`) and writes nothing outside HKCU and
  `%LOCALAPPDATA%`. Uninstalled, `local` mode only pairs from a string handed to
  the worker over `hermes/relay` (or `HERMES_RELAY_URL`), and the phase stays in
  `reconnecting`; there is no success-looking state that is not actually connected.
* The launcher is a `.bat`, so on Windows Chrome starts the host through
  `cmd.exe /c` (the same shape Google's own native-messaging example installs).
  It pins absolute paths, so no shell lookup happens — but a machine where
  `cmd.exe` is blocked by policy would need a native launcher instead.
